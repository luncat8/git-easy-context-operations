# 0.3 plan - interactive context menu editor

**Status: PLAN ONLY. Nothing in this document is implemented** - not one line of
`src/`, `package.json` or the graph-menu script is touched by it. The repo is busy
with other work; this file is the review artifact for the next free slot.

**TL;DR** - the popup VS Code draws cannot be edited by an extension, but *our
items inside it* can be hidden and shown at runtime with `setContext` + `when`
clauses. So: keep one **row id per command** in a catalogue, append
`&& (!geco.menuFilter || geco.menuVisible.<rowId>)` to every `when` clause, and
ship an editor panel that **renders the real menu from the same manifest VS Code
reads** (sections, order, separators, icons, locked built-in rows) with a toggle
switch per row. Built-in items cannot be hidden (microsoft/vscode#9285 is open
since 2016) and are shown locked. Fallbacks if the webview replica fails: native
tree checkboxes (Plan B, 4-6 h) or a `canPickMany` QuickPick (Plan C, 1-2 h) -
both reuse the whole state machine. `v1.0` review notes in section 9.

Target release: **0.3.0**. Feature name in the UI: **"Customize Context Menus..."**
(the panel calls itself *Menu Editor*).

---

## 1. Goal

Let the user decide which of *our* entries appear in the context menus, from a UI
that looks like the real menu, without editing `package.json`, without a reload,
and without ever being able to lock themselves out.

The requested shape ("best case"):

> an editor whose layout **is** the real menu - same sections, same order, same
> separators, same icons - and each of our items carries a **toggle switch**
> (checkbox) that makes the item visible or invisible in the real menu.

If that turns out not to be buildable, ship the next-best thing and leave a
`v1.0` TODO to re-review the faithful-layout route (section 9).

### 1.1 What "same layout as real" means here

"Real" = the actual `Menu` VS Code pops up. Three separate things must match:

| Aspect | Can we match it? | How |
|---|---|---|
| Which items are in it, in which section, in which order | **Yes, by construction** | the replica is *computed from the same manifest VS Code reads* (`context.extension.packageJSON.contributes.menus` + every other installed extension's manifest), so it cannot drift |
| Pixel look (colors, sizes, separators, corner radius, shadow) | **Yes, with theme variables** | webview CSS variables `--vscode-menu-*` + `--vscode-widget-shadow` (section 4.6) |
| Editing the real menu *in place* (toggling a switch inside the popup VS Code draws) | **No** | VS Code owns that widget; no API reaches it (#9285, section 2) |

So "same layout" is achievable for the *editor*, not for the *popup itself*. The
popup only ever changes as a consequence - which is exactly what the user wants.

### 1.2 Non-goals (0.3)

- Hiding **built-in** items (git's *Cherry Pick*, *Compare*, ...). Impossible for
  an extension; they are shown **locked** in the replica with an explanation.
- **Reordering** items or moving them between sections. The manifest is static
  (section 7, risk R3 has the hack that would make it possible).
- Hiding commands from the **Command Palette**. Deliberately out of scope: the
  palette is the safety net. Listed as `TODO(v1.0)` (section 9).
- Any change to the operations themselves, to the graph, or to the safety net.

### 1.3 Hard constraints (inherited from the repo)

1. Stable APIs only - the default install must keep working in VS Code, VSCodium
   and Remote-SSH without `--enable-proposed-api`
   (`src/test/core/manifest.test.ts` enforces this).
2. Core logic stays pure TypeScript behind the `UI` interface, testable without
   an editor (`src/core/` + `src/test/core/`, throw-away repos, no VS Code).
3. The manifest and the code must not drift - every new contribution gets a test
   that fails loudly (same spirit as `manifest.test.ts`).
4. Adding the feature must be a **no-op for anyone who never opens the editor**:
   with default settings the menus are byte-for-byte the 0.2 menus.

## 2. What VS Code allows (researched, with sources)

| # | Question | Answer | Source / how we know |
|---|---|---|---|
| 1 | Can an extension hide/show **its own** contributed menu items at runtime? | **Yes.** Menu contributions are static manifest data, but `when` clauses are evaluated live; the sanctioned mechanism is a custom context key created with `setContext` and referenced from the `when` clause. | VS Code docs, *when clause contexts* ("Check a setting in a when clause", "Add a custom when clause context" via `setContext`) and microsoft/vscode#110218: *"At runtime the extension can use context keys it creates via the setContext command together with when clauses to hide its contributed items dynamically."* |
| 2 | Can an extension hide items contributed by **other** extensions or by VS Code itself? | **No.** The feature request for user-configurable menus is microsoft/vscode#9285 (opened July 2016, milestone *Backlog*, still **open**). | fetched issue #9285; labels `api`, `feature-request`, `menus` |
| 3 | Can an extension change the **order/group** of items at runtime? | **No**, `group`/`order` are manifest-only. A workaround exists (contribute the same command twice with mutually exclusive `when` clauses and different groups) - fragile, see risk R3. | contribution point `contributes.menus`; `apply-graph-menu.mjs` already writes groups at *build* time |
| 4 | Can a `when` clause read a setting directly? | Yes - `config.<setting-id>`, but only booleans and the key must be a *declared boolean setting*. We would need one setting per menu item (~20) - pollutes the settings UI and Settings Sync. **Rejected** (see 4.7). | docs, *Check a setting in a when clause* |
| 5 | Can a webview look like a VS Code menu? | **Yes.** Theme colors are exposed to webviews as CSS variables, and the menu colors are part of the theme API: `menu.background`, `menu.foreground`, `menu.selectionBackground`, `menu.selectionForeground`, `menu.selectionBorder`, `menu.separatorBackground`, `menu.border`, plus `widget.shadow`, `contrastBorder`, `disabledForeground`, `descriptionForeground`. | theme color reference (*Menu Bar colors*, *Base colors*); the `--vscode-<id with dashes>` form is the webview variable |
| 6 | Native checkbox UI without a webview? | **Yes** - `TreeItem.checkboxState`, `TreeDataProvider.onDidChangeCheckboxState` and `TreeViewOptions.manageCheckboxStateManually` were finalized in 2023 (issue #116141 → #186164). Far below our `engines.vscode: ^1.94.0`. | microsoft/vscode#116141, #186164 |
| 7 | Do the built-in Source Control Graph menus still need the proposed API? | Unchanged from 0.2: yes, and the graph *build* keeps them (`scripts/apply-graph-menu.mjs`). Our editor must cover those entries too, and stay in sync with the patcher script. | `src/core/graphMenu.ts`, `scripts/apply-graph-menu.mjs` |
| 8 | How much manifest does the replica need? | It needs the *effective* menu: ours **plus** what other installed extensions contribute to the same menu key (e.g. the built-in `git` extension contributes to `scm/historyItem/context`). Those are readable at runtime from `vscode.extensions.all[i].packageJSON`. VS Code *core* (non-extension) entries are not readable - accepted gap, they are marked by omission. | `vscode.extensions.all` is a stable API |

Consequence: the whole feature is **`when`-clause surgery in the manifest + a
context-key state machine**, and the UI is a *view* of that state. Nothing more
exotic is required - which is why both the fancy and the cheap variant are cheap.

## 3. The three candidate designs

### A. "Replica" webview panel - **RECOMMENDED**

A webview panel that draws the real menu (sections, separators, icons, locked
built-in rows) and puts a toggle switch on every row that belongs to us.

- **Pros**: satisfies the "best case" literally; the layout is generated from the
  manifest, so it stays truthful; room for search, presets, reset, per-row `ⓘ`
  showing the exact `when` clause; can later host palette/reorder features.
- **Cons**: first webview in the repo → new asset pipeline (`media/`), CSP, a
  second esbuild entry point, and visual drift when VS Code changes its menu
  metrics. Rough effort: 15-22 h for the feature, 18-28 h with all polish
  (section 11).

### B. Native tree view with checkboxes - **FALLBACK (Plan B)**

A second group in the existing `geco.history` view ("Menu Editor") that lists
sections as parents and items as checkbox rows.

- **Pros**: ~4-6 h, zero new files (one provider + `checkboxState`), native look
  and native a11y, no assets, no CSP, works everywhere the view works.
- **Cons**: a tree is not a menu - no separators, no inline icons of the real
  items, no "locked built-in rows", switches are checkboxes at the row start.
  Layout fidelity maybe 50%.

### C. QuickPick (`canPickMany`) - **EMERGENCY** (Plan C, ~1-2 h)

One `showQuickPick` per surface with `canPickMany`, group labels as separators.

- **Pros**: 60 lines, no new files, instantly usable.
- **Cons**: not a replica at all (a filtered list over the screen's center),
  modal, no "apply immediately while looking at it" feeling.

### Decision rule

Ship **A**. If, during Phase 0/3, any of these turn out true, fall back to **B**
(and write the `v1.0` TODO from section 9):

- the webview cannot reproduce the menu metrics close enough to be convincing, or
- the asset pipeline (CSP + font + `.vscodeignore` + two bundles) is judged too
  much maintenance for the value, or
- the panel cannot be made to survive theme/zoom changes without per-release CSS
  churn.

**C** exists only as a stopgap if the repo needs something *now*.

## 4. Anatomy of plan A

### 4.1 The mechanism

1. Every entry we contribute gets a **row id** (a stable string; initially the
   command id, e.g. `geco.forcePushHard`, because one row = one command).
2. One context key per row: `geco.menuVisible.<rowId>` → `true` = show.
3. Every `when` clause of that entry gets one fragment appended:

   ```
    && (!geco.menuFilter || geco.menuVisible.<rowId>)
   ```

   `geco.menuFilter` is a single guard key, set to `true` once the state machine
   has run. Before activation, after a crash, or with the extension disabled the
   key is `undefined` → `!undefined` is `true` → **everything shows** (fail-open).
4. Submenu parent entries (`submenu: geco.commitSubmenu` in `scm/title`,
   `scm/sourceControl`, `scm/repository`, `timeline/item/context`) get
   ` && geco.menuHasItems.<submenuId>`, a *derived* key that is `false` when the
   user hid everything inside - so the parent never opens an empty menu.
5. The editor writes the setting `geco.hiddenMenuItems` (string array, user scope,
   default `[]`), and calls `setContext` for the changed keys. VS Code re-evaluates
   the open/later menus immediately - no reload, no window restart.

### 4.2 The exact manifest diff

Only `when` clauses change; nothing is added or removed except the two new
commands and the new setting.

| Menu key | Entries | Fragment appended |
|---|---|---|
| `view/item/context` | 24 entries (commit / branch / backup rows) | ` && (!geco.menuFilter \|\| geco.menuVisible.<rowId>)` |
| `view/title` | `refresh`, `showBackups`, `undoLastOperation`, `explainMenus`, `enableGraphMenu` | same |
| `view/title` | new `customizeMenus` | **not toggleable** (`required`) |
| `geco.commitSubmenu` | 14 entries | same |
| `geco.branchSubmenu` | 8 entries | same |
| `scm/title`, `scm/sourceControl`, `scm/repository`, `timeline/item/context` | the 4 `submenu:` entries | ` && geco.menuHasItems.geco.commitSubmenu` |
| graph build (`scripts/apply-graph-menu.mjs` → `scm/historyItem/context`, `scm/historyItemRef/context`, `scm/history/title`) | 16 generated entries | same two fragments, written by the patcher |

Example (`view/item/context`, commit row):

```jsonc
// before
{ "command": "geco.forcePushHard", "when": "view == geco.history && viewItem =~ /^geco\\.commit/", "group": "5_remote@2" }

// after
{ "command": "geco.forcePushHard",
  "when": "view == geco.history && viewItem =~ /^geco\\.commit/ && (!geco.menuFilter || geco.menuVisible.geco.forcePushHard)",
  "group": "5_remote@2" }
```

Because one row = one command, **one switch** removes e.g. *Force Push (--force)*
from the sidebar commit menu, the branch menu, the Source Control title submenu,
the Timeline and (in the graph build) the Source Control Graph at once. That is
what a user means by "I don't want this item". Per-surface granularity
(`geco.menuVisible.<surface>.<rowId>`) is a later refinement (section 9, TODO 2),
the storage format already allows it.

### 4.3 The row catalogue (single source of truth)

`src/core/menuCatalog.ts` lists every toggleable row:

```ts
export interface MenuRow {
	/** Stable id - also the setting value. NEVER renamed, NEVER reused. */
	id: string;                      // 'geco.forcePushHard'
	command: string;                 // 'geco.forcePushHard'
	label: string;                   // 'Force Push (--force)...'  (fallback for tests/tooltips)
	icon?: string;                   // codicon id, e.g. 'warning'
	/**
	 * Where it shows up - the *surfaces* below, so a submenu is expanded into
	 * the surfaces that show it. Derived from the manifest at runtime; listed
	 * here for tests/docs.
	 */
	surfaces: readonly MenuSurfaceId[]; // ['view.commit', 'scm.title', 'timeline.commit', 'graph.commit']
	/** Cannot be hidden (the way back). */
	required?: boolean;              // only 'geco.customizeMenus'
	/** Only contributed by the +graph build. */
	graphOnly?: boolean;             // 'geco.renameBranch' on scm/historyItemRef/context
}

/** The `when` fragment every entry of this row must carry. */
export function visibilityFragment(id: string): string {
	return `(!geco.menuFilter || geco.menuVisible.${id})`;
}
```

Surfaces (the editor's pages) are declared once too, with the exact `when`
context VS Code uses for them, so the replica can filter the manifest
accordingly:

```ts
export const MENU_SURFACES = [
	{ id: 'view.commit',     label: 'Source Control → Git Easy Ops → commit',  menuKey: 'view/item/context',   match: /^geco\.commit/ },
	{ id: 'view.branch',     label: '… → branch row',                          menuKey: 'view/item/context',   match: /^geco\.branch/ },
	{ id: 'view.backup',     label: '… → recovery point / journal row',        menuKey: 'view/item/context',   match: /^geco\.backup/ },
	{ id: 'view.title',      label: '… → view title (⋯ / icons)',              menuKey: 'view/title' },
	{ id: 'scm.title',       label: 'Source Control title (⋯) → Git Easy Ops', menuKey: 'scm/title',           expands: 'geco.commitSubmenu' },
	{ id: 'scm.repository',  label: 'Source Control repository row → …',       menuKey: 'scm/repository',      expands: 'geco.commitSubmenu' },
	{ id: 'scm.sourceControl', label: 'Source Control panel → …',              menuKey: 'scm/sourceControl',   expands: 'geco.commitSubmenu' },
	{ id: 'timeline.commit', label: 'Timeline → commit row → …',               menuKey: 'timeline/item/context', expands: 'geco.commitSubmenu' },
	{ id: 'graph.commit',    label: 'Source Control Graph → commit   (+graph)',menuKey: 'scm/historyItem/context',   graphOnly: true },
	{ id: 'graph.ref',       label: 'Source Control Graph → branch   (+graph)',menuKey: 'scm/historyItemRef/context', graphOnly: true },

```

`surfaces` in `MenuRow` is *checked*, not authored twice: the test derives it from
`package.json` (and from `apply-graph-menu.mjs` for the graph ones) and compares.

### 4.4 Safety rails

| Rail | Rule |
|---|---|
| Fail-open guard | `geco.menuFilter` must be `true` for anything to be hidden. Not set ⇒ nothing hidden. |
| Required rows | `required: true` (only `geco.customizeMenus`) cannot be switched off; the switch is rendered disabled with the reason. |
| Last item of a menu | `menuVisibility.canHide(state, id)` is `false` when it is the final visible item of a surface; the switch is disabled. |
| Empty submenu | Derived key `geco.menuHasItems.geco.commitSubmenu` hides the parent entry if the state is hostile anyway (e.g. hand-edited settings). |
| Unknown ids | Ids in `geco.hiddenMenuItems` that this build does not know are **kept**, not pruned (survives downgrade); the panel shows one line "1 saved id is unknown to this version - kept". |
| Reset | `Reset this menu` / `Reset all menus` empties `geco.hiddenMenuItems` and clears every key. Also reachable from the palette and from `Why Don't I See the Menus?`. |
| Getting back | The editor is reachable from: palette (`Git Easy Ops: Customize Context Menus...`), our view title icon (`$(settings-gear)`, `view == geco.history`), the Source Control title, and **every context menu we contribute** ("Customize This Menu..." as the last entry) - so the panel can be opened from the very menu the user wants to trim. |
| Nothing else breaks | Hiding an item never disables its command: palette, keybindings and programmatic use keep working. |

### 4.5 The layout engine (why it cannot drift)

`src/core/menuLayout.ts` - pure function, no VS Code import:

```ts
export interface ReplicaMenu {
	surface: MenuSurfaceId;
	title: string;
	groups: { id: string; order: number; rows: ReplicaRow[] }[];   // groups in the real order
	warnings: string[];                                            // e.g. 'graph build not installed'
}
export interface ReplicaRow {
	kind: 'ours' | 'foreign';
	rowId?: string;          // ours only -> the switch
	label: string;           // resolved through vscode.l10n / catalog fallback
	icon?: string;
	when?: string;           // shown behind the ⓘ
	enabledInGraphOnly?: boolean;
}

export function buildReplica(menus: MenuContributions, catalog: MenuCatalog, options: {
	surfaces: readonly MenuSurfaceDeclaration[];
	expansions: Record<string, MenuContributions>;   // submenu contents
	foreign?: MenuContributions;                     // other extensions' manifests
	graphBuildInstalled: boolean;
}): ReplicaMenu[];
```

- Groups come from `group` (`"5_remote@2"` → id `5_remote`, order `2`), sorted by
  VS Code's own rule (group prefix, then `@order`, `inline` last). Sections are
  rendered as separators; group **names** are shown as faint labels because the
  real menu has no headings - the label is opt-out via a "show section names"
  switch (default on in the editor, honest to the real menu in preview mode).
- Foreign rows are everything other extensions (built-in `git`, our own graph
  build) contribute to the same key. They render normally but **locked**.
- `menus` comes from `context.extension.packageJSON.contributes.menus`, so the
  replica shows what *this installed build* really contributes - the publishable
  and the +graph build therefore look different, as they should.

### 4.6 The webview

`src/vscode/menuEditorPanel.ts` (thin) + `src/webview/menuEditor.ts` (renderer,
bundled to `media/menuEditor.js`) + `media/menuEditor.css` + `media/codicon.ttf`.

- Singleton panel (`createWebviewPanel`, `reveal()` if it exists), opened with
  `preserveFocus: true` so right-click → *Customize This Menu...* does not move
  the caret, and scrolled/selected to the surface it was opened from.
- **CSP**: `default-src 'none'; style-src ${webview.cspSource}; font-src ${webview.cspSource}; script-src 'nonce-...'; img-src ${webview.cspSource} data:;`
  - no `unsafe-eval`, no remote URLs, `localResourceRoots: [media/]`.
- **Visual fidelity** (all from theme variables, so light/dark/high-contrast and
  every zoom level work):
  `background: var(--vscode-menu-background)`, `color: var(--vscode-menu-foreground)`,
  `border: 1px solid var(--vscode-menu-border)`,
  `box-shadow: 0 2px 8px var(--vscode-widget-shadow)`,
  row hover/selection `var(--vscode-menu-selectionBackground)` /
  `var(--vscode-menu-selectionForeground)` (+ `--vscode-menu-selectionBorder` for
  high contrast), separator `1px solid var(--vscode-menu-separatorBackground)`,
  disabled/locked rows `var(--vscode-disabledForeground)`,
  focus ring `var(--vscode-focusBorder)`, `contrastBorder` respected.
  Row metrics (≈ 24 px row height, 4 px menu padding, 3-4 px corner radius) are
  **measured against a real screenshot in Phase 0** and pinned in one CSS block.
- **Icons**: `@vscode/codicons` (devDependency) is copied into `media/` by the
  build, so both our `icon` codicons and the foreign entries' codicons
  (`"$(git-commit)"` from git's manifest) render exactly as in the real menu.
  Fallback if the ~90 KB font is unwanted: inline SVG for our rows, generic glyph
  for foreign rows.
- **Interaction**: surface selector (tabs = the 10 surfaces, graph ones badged
  *needs +graph build*), search box, "show hidden items" (default on - hidden
  rows stay visible in the editor, dimmed, switch off), `Preview` mode (hides all
  switches, shows the menu exactly as it will appear), `Reset this menu`,
  `Reset all`, per-row `ⓘ` (tooltip with label, `when` clause and context key),
  status line `8 of 12 items visible in this menu · changes apply immediately`.
- **A11y**: `role="switch"`, `aria-checked`, full keyboard operation
  (Tab/↑↓ between rows, Space/Enter toggles, `aria-live="polite"` status), no
  meaning carried by color alone, `prefers-reduced-motion` honoured.
- **Batching**: the renderer posts `{type:'apply', changes:[{rowId, visible}]}`
  (a bulk "hide all in this section" is one message, one settings write). The
  extension replies with `{type:'state', ...}`; the panel keeps no state of its
  own beyond scroll/selection (`getState`/`setState`).

### 4.7 Persistence

New setting (declared in `contributes.configuration` and in
`src/core/config.ts` → `CONFIG_KEYS` + `DEFAULT_SETTINGS`, which the manifest test
pins):

```jsonc
"geco.hiddenMenuItems": {
  "type": "array",
  "items": { "type": "string" },
  "default": [],
  "scope": "window",
  "markdownDescription": "Menu items of Git Easy Ops hidden from the context menus (row ids, e.g. `geco.forcePushHard`). Maintained by **Git Easy Ops: Customize Context Menus...** - edit by hand at your own risk. An unknown id is kept, so downgrading does not lose it."
}
```

- Written to **User** scope by default; a "this workspace only" checkbox writes to
  Workspace scope (`scope: "window"` permits it). Rationale: hiding the two
  `forcePush` variants in a work repo should not change the home repo.
- A settings change (also from another window, or from Settings Sync) triggers
  `onDidChangeConfiguration` → the state machine re-applies all context keys →
  every window converges. Writes are idempotent, so no event loop.
- Rejected alternative: one boolean setting per item + `config.geco.*` in the
  `when` clauses. Rejected because it adds ~20 settings to the settings UI and to
  Settings Sync, and because the ids would have to be re-generated whenever a
  command is added.
- Alternative kept in reserve: a single context key holding the **array** of
  hidden ids, referenced as `rowId not in geco.hiddenMenuItems` (the `in`/`not in`
  operators exist, and `setContext` accepts arrays). Fewer `setContext` calls,
  less debuggable in *Inspect Context Keys*, and every clause needs the guard
  twice - so it is plan **B'**, not the default.

## 5. Phases

Each phase is independently shippable to the branch and leaves the extension in a
working state; every phase ends with `npm run check-types && npm test` green.

### Phase 0 - spike (1-2 h, throw-away code)

- [ ] Verify `setContext` re-evaluates the *Source Control Graph* commit menu of
      an installed extension without a reload (the #110218 statement is about
      contributed items in general; confirm on the exact key we use).
- [ ] Verify the guard form `(!geco.menuFilter || geco.menuVisible.x)` parses and
      behaves fail-open when neither key exists.
- [ ] Measure the real context menu: row height, paddings, radius, shadow, font
      size - in default dark, light and high contrast - and pin the numbers.
- [ ] Confirm `TreeItem.checkboxState` + `manageCheckboxStateManually` behaviour
      in a tree view *with* `canSelectMany: true` (needed if Plan B is used).
- [ ] Check whether the integration test can read context keys
      (`vscode.commands.executeCommand('getContextKeyInfo')`); if not, the smoke
      test asserts the setting + the panel state instead.

*Exit*: a short note appended to this file with the measured numbers and any
surprise; decision A/B/C confirmed.

### Phase 1 - catalogue + `when` fragments (3-5 h)

- [ ] `menuCatalog.ts`, `menuVisibility.ts` (pure, no VS Code import).
- [ ] Apply the fragments to `package.json` and `scripts/apply-graph-menu.mjs`
      (mechanical; a small one-off script may generate them, but the result is
      committed as plain JSON so no build step is added).
- [ ] Tests: `menuCatalog.test.ts`
      - every row id is unique, ids are frozen against an explicit list;
      - every `command` exists in `contributes.commands`;
      - each row's `surfaces` equals what the manifest actually contributes
        (this is the drift test - it fails the moment someone adds a menu entry
        without a row or a fragment);
      - the graph script's `GRAPH_MENUS` use exactly the same fragments;
      - every fragment matches the restricted grammar
        `(!geco.menuFilter || geco.menuVisible.<id>)` (regex), so the evaluator in
        the tests stays honest;
      - `required` rows (`geco.customizeMenus`) are never hidden by the default
        state.
- [ ] `menuVisibility.test.ts`: `evaluateFragment(fragment, keys)` truth table -
      default state ⇒ **every** fragment is `true` (the "no-op for non-users"
      acceptance criterion, stated as a test).
- [ ] Tests for `canHide` (last item of a surface, required rows) and for
      `menuHasItems.<submenu>`.

*Exit*: `npm test` green, the shipped menus are unchanged with default settings.

### Phase 2 - state machine + persistence (3-4 h)

- [ ] `geco.hiddenMenuItems` in `config.ts` (CONFIG_KEYS + DEFAULT_SETTINGS) and
      `package.json`; `normalizeHiddenItems()` tolerant of garbage input.
- [ ] `menuContext.ts`: `applyMenuContext(state, setContext)` - writes every
      `geco.menuVisible.*`, the derived `geco.menuHasItems.*`, then
      `geco.menuFilter = true` **last** (so a half-applied state is never visible).
- [ ] `extension.ts`: apply on activation; re-apply on
      `onDidChangeConfiguration` (debounced ~250 ms); register
      `geco.customizeMenus` **outside** the repo-dependent `run()` helper (the
      editor must work with no repository open).
- [ ] Tests: toggle → setting written → keys correct; reset; unknown-id
      preservation; no-op when already in the target state (no write loops).

*Exit*: hiding an item by hand-editing the setting works end to end (before any
UI exists) - a good, testable milestone.

### Phase 3 - the panel (6-10 h)

- [ ] `menuLayout.ts` + `menuLayout.test.ts` against the **real** `package.json`:
      surfaces, group order, separators, foreign rows, expansion of the two
      submenus, graph-only badging.
- [ ] `menuEditorPanel.ts`, `src/webview/*`, `media/menuEditor.css`, esbuild
      second entry point + font copy, `.vscodeignore` check.
- [ ] Commands: `geco.customizeMenus` (palette, view title, Source Control title,
      last entry of every context menu we contribute: *"Customize This Menu..."*).
- [ ] Wire toggles → Phase 2 state machine; panel refreshes from
      `onDidChangeConfiguration` (so two windows agree).
- [ ] Smoke test: the panel opens, one message toggles a row, the setting changed,
      `Reset all` restores `[]`.

*Exit*: the acceptance demo - right-click a commit, pick *Customize This Menu...*,
switch *Force Push (--force)* off, watch it vanish from the real menu while the
panel stays open, click *Reset*, watch it come back.

### Phase 4 - polish (3-6 h, optional, cut freely)

- [ ] Presets (`Everything` / `Messages only` / `Minimal`) - one settings write.
- [ ] Search across all surfaces; "show me every surface this command appears in".
- [ ] "This workspace only" scope selector; JSON copy/paste of the setting.
- [ ] Manage the rows of our **own** tree view with the same switches (those are
      rendered dynamically, so this is pure core filtering).
- [ ] `Why Don't I See the Menus?` gains a section: "Some items may be hidden -
      *Customize Context Menus...* → Reset all".

### Phase 5 - docs & packaging (2-3 h)

- [ ] `README.md`: new section + settings table row; `Known limits` gets the
      "built-in items cannot be hidden" paragraph with the #9285 link.
- [ ] `CHANGELOG.md`: 0.3.0 entry; `AGENTS.md` if the build gains steps.
- [ ] Both builds: `npm run package` **and** `npm run package:graph`
      (`node scripts/apply-graph-menu.mjs status` must still report a publishable
      manifest afterwards); `node scripts/run-vscode-tests.mjs`.
- [ ] Manual QA matrix: VS Code + VSCodium, dark/light/high-contrast, 100%/200%
      zoom, no repository open, remote SSH, publishable build and +graph build,
      two windows open at once.

## 7. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | A forgotten fragment somewhere → an item can never be hidden (or an item disappears unexpectedly). | The drift test (Phase 1) enumerates the manifest and fails with the exact JSON path. |
| R2 | Webview visual drift when VS Code changes menu metrics. | All colors/sizes come from theme variables and live in one CSS block; a `vscode` engine bump is the trigger to re-check (noted in AGENTS.md). |
| R3 | Users asking for **reordering** / moving items between sections. | Documented as impossible; the hack (duplicate entry with `group` X vs Y and mutually exclusive `when` clauses) is written up as `TODO(v1.0)`, with the note that it is *only* safe if `A && B` is provably false for every state - `!=`/`==` against an unset key must be verified first (Phase 0 style spike). |
| R4 | The fail-open guard could mask a broken state machine ("nothing is ever hidden"). | `geco.menuFilter` is set after every apply and logged in the output channel; *Why Don't I See the Menus?* reports its value. |
| R5 | First webview in the repo = new failure modes (CSP, fonts, packaging). | `media/**` inclusion checked in both `.vsix`, smoke test opens the panel, no remote resources, no `unsafe-eval`. |
| R6 | Two windows write the setting simultaneously. | Last write wins (settings semantics), every window re-applies on change; documented limit. |
| R7 | A user hides too much and blames the extension. | Required row, "last item" rule, reset in three places, `explainMenus` pointer, README. |

## 8. Known limits to document (Phase 5)

- Built-in items (git's *Cherry Pick*, *Compare*, *Checkout*, ...) cannot be
  hidden by an extension - VS Code has no API for it (microsoft/vscode#9285,
  open since 2016). They are shown locked in the editor.
- Hiding is per **command**, not per menu: one switch removes the item everywhere
  it appears (that is the intent; per-surface overrides are a `v1.0` idea).
- Menu **order and sections** are fixed by the manifest; the editor cannot move
  items.
- Hiding affects context menus only - the Command Palette, keybindings and other
  extensions calling our commands are untouched.
- Immediately after startup (and while the extension is disabled or crashed)
  everything is visible; the state is applied a moment later (fail-open by
  design).
- The palette/replica shows the items of the **installed build**; the
  `+graph.vsix` build has 16 more entries.

## 9. TODO register for **v1.0** (the requested review note)

These are the notes to leave in the repo at implementation time - a comment block
in `src/core/menuCatalog.ts`, a `TODO(v1.0)` entry here, and one bullet in
README → *Known limits*:

1. **TODO(v1.0) - re-review "same layout as real".**
   The editor replicates the menu; it cannot edit the popup VS Code draws. Review
   once a release: (a) does microsoft/vscode#9285 (*User configurable menus*, open
   since 2016) or #110218 (*dynamic submenus*) land, or does a new stable API
   expose menu contributions for editing? If yes, drop the replica and edit the
   native menu - that would also allow hiding **built-in** items, which this
   design cannot do. (b) If the replica stayed, judge its fidelity against the
   real menu on the current VS Code and decide whether the webview or plan B
   (native tree checkboxes, section 3) should be the long-term UI.
2. **TODO(v1.0) - per-surface granularity.** Storage is a flat list of row ids.
   If users ask for "keep *Squash* in the sidebar but hide it in the graph",
   introduce `geco.menuVisible.<surface>.<rowId>` keys: the setting format already
   tolerates it and unknown ids are preserved.
3. **TODO(v1.0) - Command Palette and keybindings.** Hiding from the palette is
   possible (`contributes.menus.commandPalette` + `when`) but was deliberately
   skipped: the palette is the way back. Re-evaluate with a "you can always get it
   back from the palette" warning in the UI.
4. **TODO(v1.0) - reorder / move between sections.** Only possible via duplicated
   entries with complementary `when` clauses. Re-evaluate only if VS Code offers
   real support, or if the mutual-exclusion proof (R3) can be automated.
5. **TODO(v1.0) - icons.** Decide between the copied `@vscode/codicons` font
   (fidelity, ~90 KB) and inline SVG (no asset); revisit when the contract of the
   webview assets is touched next.
6. **TODO(v1.0) - localisation.** The replica currently falls back to catalogue
   labels (English). Once the repo grows a `package.nls.json`, resolve every
   label through the VS Code l10n bundle (the manifest is not the only source
   then).

`menuCatalog.ts` + `menuVisibility.ts` **entirely** - only the renderer differs.

safety rails) is written once, and the UI over it is replaceable.
